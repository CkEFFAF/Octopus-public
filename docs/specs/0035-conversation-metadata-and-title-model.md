## 1. Summary

新增「设置 → 会话整理」，用用户选择的文本模型异步生成简短标题与摘要。每个会话提供一份可追溯、可更新的概览，以及按时间查看的关键事件。用户看到易读信息，Agent 读取同源结构化数据。

需要快速回答六件事：**在做什么、为什么做、已经做到哪里、卡在哪里、下一步做什么、这段时间发生了什么。**

标题用于识别会话，目标与概览用于理解内容，进度来自实际记录，时段摘要用于回顾变化。生成摘要不能改变任务执行、授权或验收状态。

## 4. Decision

1. **设置项按账号归属。** 会话整理使用会话所属用户的配置、Provider 和用量归属；共享专家不借用另一位专家所有者的密钥做该用户的会话整理。
2. **独立的轻量模型调用。** 标题/摘要是无工具的辅助调用，不能执行代码、创建子 Agent 或发布产物。复用现有模型适配器和文本调用入口；不新增模型 SDK 或外部队列。
3. **事实投影与模型文字分开。** 正在运行、等待批准、Job 结果等来自执行系统；模型只概括语义与提出待办。计划打勾属于声明，不能自动视为验证通过。
4. **人工编辑优先。** 标题锁定，目标/说明等字段单独保存人工覆盖；模型刷新只替换自动字段。
5. **同一个服务供 UI 和 Agent 使用。** 没有一套仅在浏览器 localStorage 的摘要，也没有另一套在 Agent 文件中的会话进度。
6. **标题保持稳定。** 默认首次生成；检测到明确目标变化后提供新标题建议，由用户应用。首版不在每轮对话中自动改名。
7. **使用当前事件与存储体系。** 新增可重建的元信息投影与持久后台任务，复用 0034 的任务详情入口，不另造任务管理系统。

推荐默认值是本规格的设计建议，不代表已经应用或用户已经验收。无阻塞性未决产品项。

## 5. Design：设置与标题

### 5.1 设置入口

「设置 → 会话整理」位于「模型」附近。模型页面增加一个指向此页的「会话标题与摘要」入口，避免把后台整理模型和聊天主模型混在一起。

```text
会话整理

标题生成                 开启
标题模型                 跟随账号默认模型 ▾
更新方式                 首次生成；目标变化时建议更新

会话概览与时段摘要       开启
摘要模型                 与标题模型相同 ▾
自动更新                 对话或任务有新进展时

历史会话                 选择会话后整理…
                                  取消   保存
```

| 字段 | 选项 / 推荐默认 |
|---|---|
| 自动生成标题 | 开；可独立关闭 |
| 标题模型 | 跟随账号默认模型 / 当前账号已配置的指定文本模型 |
| 自动更新概览 | 开；和标题开关独立 |
| 摘要模型 | 与标题模型相同 / 跟随账号默认模型 / 指定文本模型 |
| 既有会话处理 | 默认不批量调用；打开未整理的旧会话时提供「生成概览」，支持用户选择一批进行整理 |

只列能接受文本的模型。显示 Provider 与模型名称，保存稳定 `provider/model` 引用，不保存密钥。跟随账号默认模型时展示当前解析值；默认模型缺失时提示去配置，不能默默借用其他账号模型。标题关闭时，摘要的「与标题模型相同」仍解析标题模型配置。

切换模型只影响后续任务；已有摘要继续保留生成模型与时间。指定模型失效时保留旧结果并提示，不自动切换到更贵模型。复用现有用量记录，增加 `purpose=thread_title|thread_brief|thread_digest`，费用未知时只显示实际 Token，不估算伪精确金额。

### 5.2 标题生命周期

1. 首条消息持久化后立即出现占位标题。去掉模板封套、纯附件占位和多余空白，再按现有 40 字符规则截取；纯附件使用本地化「附件讨论」占位。
2. 首轮回复终结、失败或进入持久等待态后，使用首问和已公开的回应生成主题标题。无可用回应时只依据请求；不为取标题等待整段长任务。
3. 中文通常以 8–18 字表达「对象 + 目的/动作」，英文通常 3–8 个词，统一不超过现有 40 字符上限。上述范围是写作目标，不是汉字/英文混合字符串的强校验。
4. 不带问候、首问全文、Markdown、引号、状态、日期或「新会话」等无效前缀。编号与专有名词仅在帮助识别时保留。输出为空、超长或结构无效时拒绝写入，保留占位标题。
5. 首次生成后保持稳定。新目标通过概览的 `objective_version` 体现；标题建议单独展示，用户「应用」才替换。
6. 重命名设置 `title_source=user` 并推进 `title_revision`。自动任务提交必须同时匹配已捕获的标题版本和允许覆盖的来源；用户改名发生在模型调用期间也有效。
7. 用户可选择「重新生成标题」预览建议，或「恢复自动命名」。前者不解除锁定；后者明确解除。

示例：首问「设置里面加一个，会话标题更新负责的模型选取……」→ **「会话标题与进度管理」**。运行状态放在旁边，标题不反复变成「正在设计 / 设计完成」。

## 6. Design：会话信息结构

### 6.1 展示层级

| 层级 | 内容 | 默认展示位置 |
|---|---|---|
| 身份 | 简短标题、所属 Agent/项目、通道、创建/最近活动时间 | 会话列表与详情 |
| 内容 | 一句概括、当前目标、范围与用户约束 | 列表一句概括；「会话概览」完整显示 |
| 进度 | 当前阶段、已完成事项、进行中、待办、等待谁、阻塞原因、下一步 | 列表状态；概览中详细显示 |
| 结论 | 关键决定、重要发现、已放弃的方案及原因 | 概览折叠段落，带来源 |
| 成果 | 已登记的文件/资源/链接、版本、产生时间、验证与验收情况 | 复用现有成果入口 |
| 回顾 | 指定区间的变化、关键事件、遗留项 | 概览的「时间回顾」标签 |
| 可信度 | 更新时间、覆盖到的消息/事件、缺失范围、人工/自动来源 | 概览底部；过期时靠近状态显示 |

列表默认每项控制为两行：第一行「标题 + 状态」，第二行「一句概括或下一步 + 相对时间」。原始 ID、版本、Token 等留在详情的技术信息中。

桌面在现有聊天标题旁增加「会话概览」按钮；打开右侧抽屉。0034 的运行简略入口、详细任务弹窗继续负责实时运行。概览的「查看运行详情」跳到原入口。375px 使用单列全屏抽屉，保持显式关闭/返回，不依赖悬浮或双击。

```text
会话标题与进度管理       设计中            [会话概览]

会话概览                         更新于 14:32 · 最新
为会话增加独立标题模型，并统一进度、摘要与事件回顾。

目标      让用户和 Agent 快速理解会话并继续推进
当前阶段  方案设计
已完成    查明标题来源；确认可复用的运行与历史记录
待办      设置项；概览存储与界面；时段摘要；回归验证
下一步    按设计实现设置与首次标题生成

[概览] [时间回顾] [决定与成果]
```

以上内容为设计示例；产品中的每一条事实必须引用实际来源。没有明确计划时显示「尚未建立计划」，不编造进度百分比；有计划时显示「已完成 2 / 5 项 · Agent 报告」，展开可见每项证据。实际验证计数单列。

### 6.2 状态语义

保存三组不同信息，避免使用一个 `status` 覆盖所有含义：

| 维度 | 值与含义 | 来源 |
|---|---|---|
| `execution_state` | idle / queued / running / waiting_user / waiting_approval / paused / failed / unknown | 当前输入回执、运行、HITL、Job 与观测；由规则投影 |
| `work_state` | unknown / in_progress / blocked / ready_for_review / completed / cancelled | 明确目标和证据；completed 需要用户确认或事先明确的可机验完成条件 |
| `freshness` | current / updating / stale / partial / unavailable | 来源版本、覆盖范围、生成任务与观测时间 |

Agent 报告「完成」先进入待验收，保留 `reported_by=agent`；验证通过记录 `verification`，用户确认记录 `acceptance`。即使所有工具正常退出，也不能自动认定整个工作完成。没有计划的一般问答不强制建立任务状态。

默认列表状态按优先级显示：待批准/待用户 → 有活动运行 → 失败/阻塞 → 待验收 → 已完成 → 排队/暂停 → 空闲/状态未知。运行已经失败但另有后台 Job 时显示「运行中 · 有异常」，详情逐项展开。离线或观测失效时附「状态待确认」，不继续宣称此刻正在运行。

一轮回复结束通常只把本轮执行置为空闲。用户明确开启新工作时推进 `objective_version`，重新显示进行中，旧目标的决定/成果留在历史。修辞上的感谢不自动取消或完成目标。

### 6.3 核心结构

`ConversationBrief` 是类型化服务响应；数据库中的 JSON 必须经过固定模型校验，不能成为任意键值垃圾箱。

```text
ConversationBrief
  schema_version, revision, thread_id, objective_version
  title { text, source, revision, suggested_title? }
  overview { one_liner, objective, scope, constraints[] }
  progress
    stage, work_state, execution_state, observation
    completed[], in_progress[], remaining[], blockers[], next_actions[]
    plan_refs[], verification[], acceptance?
  decisions[], findings[], artifact_refs[]
  manual_overrides { objective?, scope?, note? }
  provenance
    source_watermarks, coverage, generated_at, effective_model_ref
    prompt_version, visibility_scope, freshness
```

每个重要条目带 `item_id / text / source_refs / author_kind / observed_at`；任务条目尽可能引用已有 `plan_id/task_id/run_id`，不生成平行的可执行计划。用户意见、Agent 推断、工具结果的来源标签分开；缺少支撑的语义判断显示为「建议 / 待确认」。不展示模型自造的置信度百分比。

`source_refs` 是消息、事件、计划版本、验收或资源版本的稳定引用。点击时重新校验权限；来源已失效时显示「来源已不可用」。摘要中的路径只是描述，不构成文件读取授权。

## 7. Design：事件与时段摘要

### 7.1 什么值得记

仅将对进展有意义的变化整理为事件：需求提出/修改、计划建立/变更、关键决定、重要发现、可用成果产生、验证结果、错误/阻塞、等待/恢复、目标完成/重开与人工修正。

逐 Token 输出、每条命令日志与重复轮询不成为用户时间线事件。失败后的重试合并展示，保留尝试明细；同一个 ask_agent dispatch 与 collaboration invocation 复用 0034 的去重关系，不算两次工作。

事件模型：`event_id, occurred_at, recorded_at, kind, actor, objective_version, text, source_refs, outcome, supersedes?`。事件是现有记录的派生索引，不替代真实执行记录；更新以稳定来源键幂等。已记录的决定被推翻时追加变更事件，旧决定标为失效，不悄悄抹除。

### 7.2 时间回顾交互

预设「今天 / 最近 7 天 / 自定义区间」，按系统服务端时区显示绝对起止时间。今天从本地日界到当前；最近 7 天含今天及前 6 个自然日。日期型自定义结束日包含整日，服务端换算成 UTC 半开区间 `[from, to)`；未结束的当天只覆盖到观测时刻。

结果结构：

- 一段概括：这段时间围绕什么工作，主要变化是什么。
- 已推进事项与成果，附验证/验收状态。
- 新增/变更的决定，附决定时间与来源。
- 出现或解决的问题，明确仍未解决的部分。
- 区间结束时遗留的事项与下一步；不能拿现在的状态回填为过去的状态。
- 可展开的关键事件，以及生成时间、覆盖范围与缺失说明。

没有新事件显示「这段时间没有记录到新进展」，不发模型请求。区间开始前的背景允许作为单独标注的背景句，不计入区间成果。区间内开始、区间外结束的任务，在区间摘要中仍是当时的进行中；迟到回执按真实发生时间归入，并令受影响缓存过期。

时段摘要按需生成并缓存；会话没有新事实时不反复消耗模型。日事件块可作为长区间分层汇总的输入，但跨边界时只选取匹配的事件。每层保留原始来源引用与缺失范围，禁止只从上一次模型文字继续压缩。

## 8. Design：自动更新与持久化

### 8.1 更新触发与建议限额

以下是首版工程默认，集中为内部策略常量，用户无需配置一排技术参数：

| 场景 | 行为 |
|---|---|
| 首个稳定轮次 / 持久等待态 | 排入标题与首份概览；两项用同一模型时可合为一次调用，分别校验/提交 |
| 后续公开消息或关键任务事实变更 | 实时事实立即更新；语义概览标为更新中，合并后台请求 |
| 连续进展 | 概览语义生成每会话最多每 60 秒一次；触发 5 秒合并，达到间隔后处理最新完整来源快照 |
| 阻塞、验收、目标变更、人工修改 | 事实立即展示；语义摘要排入优先队列，不能延迟事实状态 |
| 空闲、旧会话列表分页、打开已有摘要 | 不因读取而重复调用模型 |
| 用户请求区间摘要 / 重新生成 | 返回任务回执，命中同版本缓存则直接复用；生成中禁止重复提交 |

标题建议不因日常进度变化生成；只在结构化目标版本改变时考虑。新会话自动整理默认开启，升级不对历史记录直接发起全量模型调用。

首版每账号并发 1 个生成请求，单请求超时 30 秒；可重试的网络/限流错误最多再尝试 2 次，按 5 秒、30 秒退避并遵守更长的服务端限流时间。鉴权失效、模型删除、非法结果不自动循环重试。手动重试仍去重。输入预算最多 12,000 tokens 且不超过模型安全可用窗口，输出最多 1,600 tokens；不兼容这些上限的适配器须使用更小的安全限制。

超过预算时按稳定来源分段，保留未处理范围与继续游标；不得悄悄只看最后几条却标全量。大区间分层处理，每个分片单独检查预算和重试上限。模型调用使用公开消息、既有摘要和已归档的事实摘要，不包含隐藏思考、密钥、原始授权令牌或未经读取许可的附件正文。

### 8.2 事实版本与后台任务

消息、计划、运行回执、成果和人工修正各有独立来源版本。不能只拿 `last_active` 或最大事件 seq 判断新鲜度：事件可原地更新，Job 结果也可能在没有新用户消息时抵达。

在相关持久来源变更的同一事务中标记会话元信息为 dirty，推进对应单调 revision，并 upsert 生成任务。生成器捕获来源版本向量、人工字段版本、标题版本与配置版本。完成后先校验：

1. 账号/会话仍存在、权限仍有效、当前策略仍允许提交。
2. 标题版本/来源允许替换，人工字段版本没有被覆盖。
3. 源版本匹配才作为最新结果提交；有新来源时可保留为旧快照，但不能替换更新的快照，立即合并下一次任务。

后台任务持久化并使用租约领取；服务重启可恢复，过期租约可重新领取；提交按来源版本与唯一键幂等。模型返回成功但落库失败后重放不会反复改名或重复事件。UI 订阅只接收提交后的 `thread_metadata.updated`，沿用现有通知通道；断线后通过 GET 取回最新快照。

### 8.3 存储建议

| 表/字段 | 用途 |
|---|---|
| `threads.title_source/title_revision/title_updated_at` | 既有标题的来源、并发保护与更新时间；保留 `threads.title` 兼容旧客户端 |
| `thread_metadata`，1:1 扩展 | 自动概览 JSON、人工覆盖、元信息 revision、来源版本向量、dirty 标记、最近生成状态 |
| `thread_semantic_events` | 可重建的关键事件索引；thread + 稳定 source key 唯一，occurred_at 可查询分页 |
| `thread_digests` | thread + visibility_scope + 区间 + 来源版本 + prompt/schema 版本的摘要缓存，含覆盖信息 |
| `thread_metadata_jobs` | 标题/概览/区间/历史回填的持久任务、去重键、租约、尝试次数、错误码 |

1:1 扩展以公共字符串 `thread_id` 关联；新资源表遵守根 AGENTS 的代理整数主键与公共字符串 ID 约定，子表外键不指向整数代理主键。所有查询须显式约束 user/agent/thread；缓存不能跨权限视图复用。

SQLite / PostgreSQL 迁移成对添加。当前基线已有 032，实施前核对发布与 watermark，按实际下一个编号或未发布迁移规则处理，不能依据 AGENTS 中旧版本例子覆盖历史迁移。

## 9. Design：服务、API 与 Agent

### 9.1 模块边界

- 新领域服务置于 `infra/conversations/`：配置解析、来源选择、事实投影、摘要生成、更新策略与后台 worker。SQL 保留在 `infra/db/repos/`。
- HTTP 在 `api/routers/` 做类型校验和权限映射；通过 SharedServices 注入领域服务，不把模型调用写进路由。
- 前端通过 `dashboard/src/api/modules/` 取数据；设置页、列表与概览共享类型，不直接 fetch。
- Harness 的无工具模型调用适配层沿用现有基础设施；如果现有工厂不能按明确 user_id 解析指定模型，先补这一个适配缝，不能使用共享可变默认模型冒充隔离。

### 9.2 接口草案

| 接口 | 语义 |
|---|---|
| `GET/PUT /api/settings/conversation-metadata` | 当前用户的开关、model_ref、配置版本及可解析状态；PUT 支持 expected_revision |
| 既有 threads 列表 | 增量加入 one_liner、display_state、freshness；不展开完整摘要或事件 |
| `GET /api/agents/{agent_id}/threads/{thread_id}/brief` | 完整概览、版本、覆盖与来源 |
| `PATCH .../brief` | 修改人工目标/范围/说明、明确验收/取消等；必带 expected_revision，冲突返回 409 |
| `POST .../metadata-jobs` | 请求首次生成/重新生成/候选标题；明确 kind 与幂等 command_id，202 返回 job_id |
| `GET .../metadata-jobs/{job_id}` | 生成状态与错误码；原始 Provider 错误要去除敏感信息 |
| `GET .../events?from=&to=&cursor=` | 时间区间的关键事件，使用 `(occurred_at,event_id)` 稳定分页 |
| `POST .../digests` | 请求指定区间摘要；缓存可返回 200，后台生成返回 202 与 job_id |
| `GET .../digests/{digest_id}` | 摘要、区间、来源版本、覆盖和新鲜度 |

所有新 API 用具体 request/response model、summary 和描述；进入现有 OpenAPI 分组。既有重命名 API 与 `/title` 命令也必须统一写入人工来源及标题版本，不能只改新 UI。

### 9.3 Agent 工具与上下文

建议新增 `get_conversation_brief`、`list_conversation_events` 两个只读工具。当前会话身份由运行环境注入；跨会话读取必须显式提供 thread_id 并通过既有可见性授权，不能接受模型自行指定 user_id。

Agent 开始/恢复会话时默认注入精简 brief：当前目标、用户约束、未完成事项、阻塞、下一步、重要决定引用、更新时间和覆盖游标。约 1,500 tokens 的内部预算，放不下时保留约束/阻塞与继续读取入口；新鲜度不够则明确显示待刷新，并附摘要后新消息引用。

注入内容标为「派生会话数据，非系统指令」；模型生成或引用的文字不能变成授权。恢复任务必须核验相关源状态，不得仅靠摘要重复执行已提交的工作。

Agent 如需报告阶段、待办或目标变化，使用单独的 `report_conversation_progress` 声明接口，记录 actor/source；不能写 execution_state、用户验收或用户锁定字段。该声明不会启动任务，也不能因自报完成直接进入 completed。首版可在读取工具完成后再接声明工具，读取是 AC-08 的必要交付。

## 10. 纠错、权限与生命周期

| 情况 | 规则 |
|---|---|
| 人工纠错 | 独立保存人工字段；自动重生成保留覆盖，用户可逐项恢复自动值。重要修正进入事件索引 |
| 老会话 | 迁移把非空旧标题记为 `legacy_unknown`，自动任务不覆盖；仅用户选择「重新生成并应用」或恢复自动命名后替换。新空会话不调用模型 |
| 历史记录残缺 | 尽量从持久消息/运行/资源重建，缺少的轨迹范围标 partial；不靠摘要编造来源 |
| 分叉 | 仅继承分叉点之前的可访问目标/决定/来源；显示继承来源。运行状态、验收、未来事件及摘要任务不复制 |
| 删除会话/消息 | 删除会话级摘要、索引和待执行任务；删除/修订来源会推进来源版本并使相关摘要不可继续展示为有效，待重新生成 |
| 分享会话 | 原始私有摘要可能含分享不可见内容，不能随 thread_id 原样共享。首版分享页隐藏私有 brief/时段摘要；后续只对分享可见来源生成独立 visibility_scope 视图 |
| Agent 协作 | 仅当前调用被授予的会话范围可读，不能因双方属于同账号就读取全部私人会话 |
| 模型/权限被撤销 | 取消尚未提交的调用结果；不暴露 Provider 密钥。已有结果的读取仍经过当前权限检查 |
| 关闭自动生成 | 停止/取消待生成项；保留已有摘要并显示其覆盖时间，真实执行状态照常更新；手动生成是一次明确请求 |
| 主模型上下文压缩 | 本功能不取代 Harness 的 compaction、持久记忆或聊天历史；摘要不能成为唯一不可恢复的信息源 |

所有用户可见固定文案进入中英 i18n。生成内容遵循会话语言；设置页的界面语言变化不自动重翻译全部历史。时间展示复用 `useServerTimezone` 与现有格式化函数。

## 12. Verification plan

后续实施至少验证这些行为，不能只断言接口返回字段存在：

1. 长中文首问 → 首轮回应 → 标题变短且语义正确；模型超时/非法输出 → 原会话回复成功，原标题保留。
2. 模型执行中人工改名；并发两次生成乱序返回；旧客户端 PATCH 和 `/title` 改名：最后都保留用户值。
3. 用户 A/B 各选模型，后台重启恢复：调用/用量/返回互不串；共享专家也不会借用另一账号模型。
4. 主回复结束但子任务/Job 仍运行；工具退出成功但验证失败；Agent 自报完成但尚未验收：三种情况都不显示目标已完成。
5. 无新消息的 Job 晚回执、事件原地更新、计划变更、消息修订：都让旧概览失效并增量更新；旧任务不能回写为最新。
6. 生成任务超时、服务重启、落库后通知丢失、幂等重试：恢复后无重复事件、无重复改名，事实状态始终可查。
7. 跨午夜、自定义结束日、夏令时、区间外完成、迟到回执、空区间、历史被裁剪、超过单页事件：区间与覆盖标识准确。
8. 人工纠错后重新生成；目标重开；从中间分叉；删除源消息；私有会话分享：人工字段和可见性符合第 10 节。
9. 真实应用：设置并保存模型，长首问产生简短标题，概览跟随实际计划/等待/成果更新，按区间回顾并跳到原文；桌面与 375px 键盘/触屏无溢出。

实施后执行根 AGENTS 要求的 `make all`，UI 类型检查/构建、相关 i18n 验证和 `/api/docs` 复核；真实模型烟测在受控会话进行，记录实际调用模型与用量。设计阶段未执行这些应用验证，不能据此宣称功能可用。

## 13. Consequences / Follow-up

- 用户无需翻阅长对话即可定位目标与下一步；Agent 获得可核验的交接入口。
- 自动整理会产生额外模型调用；通过独立选模、增量处理、限额与缓存控制，使用量可归因。
- 来源更新、人工覆盖、异步乱序与分享权限是本功能的主要工程复杂度；这些属于交付条件，不能靠漂亮文案掩盖。
- 跨多个会话的项目日报/周报、全局语义搜索、按 Agent 覆盖模型和无人值守定时推送不在本次范围。现规格的时间回顾始终限定当前会话。
