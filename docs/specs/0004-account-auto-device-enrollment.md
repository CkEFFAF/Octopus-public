## 1. 背景

用户将产品体验锚定为类似 **UU 远程**：

1. 各端（工位 / 笔记本 / GPU / 以后手机）用**同一账号登录**；
2. 启动执行端程序后，中枢**快速识别并登记**该设备；
3. 同账号下可见**全部已登记设备**，形成设备网；
4. 在设备网之上挂 **Agent：不同设备 × 不同 Agent 组合**；
5. 中枢当前落在 **Win 工位**，以后可迁到**云服务器**（整库迁移，非多中枢热切换）；
6. **手机**：现阶段只做指挥（浏览器打开 Dashboard）；可执行（自动化）为后续阶段。

现行 [0001](./0001-account-device-network.md) / [contract](../octopus/device-network-contract.md) 已提供「同账号设备网 + 派工 + 文件/桌面/命令」，但登记路径是 **配对码或账号 access_key → 显式 enroll → 长期 `odv_` 设备凭据**，并明确：

- 打开网页 / 另起 Octop 实例**不会**自动变成设备（AC-02）；
- 浏览器登录只建立**用户会话**（指挥），与原生设备客户端是两条通道；
- 首连仍有交互（AC-13 已简化为向导，但仍非「登账号即自动登记」）。

本规格描述如何把体验升级到「UU 式同账号自动登记」，而不推翻 0001 已冻结的账本边界、单中枢、凭据分离与 Agent 派工模型。

## 2. 目标体验（用户可见）

| # | 体验 | 说明 |
|---|---|---|
| TX-01 | 同一账号 | 指挥端与执行端都认**同一 Octop 账号**（`owner_user_id`），不在每台机器另建用户。 |
| TX-02 | 登入即可见网 | 任意指挥端（工位本机 / 笔记本浏览器 / 手机浏览器）登录后，设备页列出该账号下**全部已登记设备**及在线状态。 |
| TX-03 | 启动执行端 → 自动进网 | 用户在某台机器安装/启动**执行端程序**，用同一账号完成一次登录（或等价账号凭证），中枢**自动登记**该机（或恢复既有 `device_id`），无需再抄配对码。 |
| TX-04 | 快速识别 | 从执行端「已登录并连上」到指挥端设备列表出现/变绿，目标 **≤ 5s**（同网可达时）；断线重连不产生重复设备。 |
| TX-05 | 一网多指挥 | 工位 / 笔记本 / 手机只要打开**同一中枢** Dashboard，都能指挥全网 Agent 与设备。 |
| TX-06 | Agent 组合 | 对话/看板可选设备派活；专家可 `device_binding` 永久绑某台（见 device-acp）；「不同设备不同 Agent 组合」是产品层配置，不另起第二套设备身份。 |
| TX-07 | 中枢可迁 | 工位 → 云：迁移账本与设备登记表；执行端改指向新中枢地址后，用同一账号/既有设备身份重新上线（详见 0003，本规格只要求登记模型可迁移）。 |
| TX-08 | 手机分期 | MVP：**仅指挥**；后续：**可执行**（自动化能力，类豆包手机），本规格只留接口位，不承诺本阶段交付。 |

一句话口令：**账号决定「谁的设备网」；执行端进程决定「谁在被控」；浏览器会话决定「谁在指挥」。**

## 3. 现状差距（相对目标）

| 维度 | 今天（0001 + contract） | UU 目标 | 差距 |
|---|---|---|---|
| 登记触发 | 配对码 **或** access_key → `POST /devices/enroll`；用户确认权限/共享目录 | 账号登录执行端后自动登记 | 缺「账号会话驱动的自动 enroll / 恢复」路径 |
| 指挥 vs 执行 | 浏览器 JWT = 指挥；`odv_` = 设备 | 同左，但用户感知为「登同一账号」 | 需产品文案与首启向导统一成账号心智，底层仍可双凭据 |
| 重复登记 | 重连用本地 state，不新建；另开实例不自动加 | 同账号同机指纹合并 | 需明确 **device fingerprint** 与合并规则 |
| 发现方式 | 客户端主动连中枢（报到） | 「中枢快速识别已启动的执行端」 | 语义上仍是**客户端出向连接**（非扫网）；要优化的是延迟与零配对码 |
| 手机执行 | 未做 | 后续可执行 | 明确非本规格 MVP |
| 多中枢 | 明确不做热切换/跨库同步 | 单中枢，可整迁云 | 无差距（保持） |

**非差距（已具备，本规格复用）：**

- 同账号设备列表、在线心跳、授权/撤销、按 `device_id` 派工；
- 文件中继、桌面采集/键鼠（Win）、命令执行与 HITL；
- 专家 `device_binding` + 设备侧 `acp_run`（需 `--allow-acp`）；
- Linux / Win 设备包与 `start-device` 入口。

## 4. 概念模型

```
┌─────────────────────────────────────────────────────────┐
│  Control Plane（唯一中枢：工位，日后可迁云）              │
│  · 账号账本 / 设备登记表 / 授权 / 操作 ledger            │
│  · Dashboard（指挥 UI）                                  │
└───────────────┬───────────────────────────▲─────────────┘
                │ 用户会话 (browser JWT)     │ 设备通道 (odv_ + WS)
                │ 指挥、列表、派工、撤销      │ hello / heartbeat / request
┌───────────────▼────────────┐    ┌─────────┴──────────────────┐
│ Commander（指挥端）         │    │ Executor（执行端）          │
│ 工位浏览器 / 笔记本 / 手机  │    │ start-device / 设备 App      │
│ 登录同一账号即可指挥全网    │    │ 账号登录 → 自动登记/恢复    │
│ 现阶段手机 = 仅 Commander   │    │ 本地 state 持有 device_id   │
└────────────────────────────┘    └────────────────────────────┘
```

### 4.1 身份对象

| 对象 | 标识 | 生命周期 |
|---|---|---|
| Account | `owner_user_id` | 用户账号；指挥端与登记归属 |
| DeviceRegistration | `device_id` + `owner_user_id` | 账本持久；撤销后不可派新活 |
| DeviceCredential | `odv_…`（设备专票） | 登记时签发；本地 state 保存；轮换/吊销独立于账号密码 |
| CommanderSession | 用户 JWT（密码或 access_key 登录） | 短中期会话；**不能**代替设备凭据连 WS |
| DeviceFingerprint | 本机稳定指纹（见下） | 用于同机合并，避免重复登记 |

### 4.2 DeviceFingerprint（草案）

用于「同一物理机再次启动执行端」时合并到已有 `device_id`，而不是新建设备：

- 组成建议：`platform` + 稳定机器标识（Win：MachineGuid；Linux：`/etc/machine-id`）+ 可选安装实例 ID（便携包可写入 state）；
- **不**用可变 IP、不单独用主机名；
- 指纹只作为服务端合并提示；权威仍是 `device_id` + 本地 state；
- 用户主动「在本机登记为新设备」时可无视指纹强制新建（高级选项）。

### 4.3 权限与角色（相对 UU）

UU：同账号设备 ≈ 对等遥控。  
Octopus：同账号可见，但**执行能力仍受 grant**（桌面 / 文件根 / 命令 / ACP）约束；自动登记默认授予**最小权限集**（见 §6），用户可随后升级。

## 5. 流程

### 5.1 首次自动登记（MVP 主路径）

```
用户在执行端启动程序
  → 输入中枢 URL（可记忆）+ 同一账号登录
      （密码登录 或 允许 devices 的 access_key / key-file）
  → 客户端：若本地 state 已有 device_id+token → 走「恢复上线」(5.2)
  → 否则：携带账号会话向中枢请求 auto-enroll
      · 提交：name（默认主机名）、platform、capabilities、fingerprint、
        默认 permissions / roots（见 §6）
      · 服务端：校验账号；按 fingerprint 查找未撤销登记
          - 命中 → 轮换/重发设备票，返回原 device_id（合并）
          - 未命中 → 新建 devices 行 + 签发 odv_
  → 客户端写入 state，建立 WS /api/devices/connect/ws
  → 指挥端设备列表 ≤5s 内出现且 online=true
```

**与现网 API 的关系（实现期二选一或并存，评审时拍板）：**

- **方案 A（推荐最小改动）：** 扩展 `POST /devices/enroll`：允许「用户 JWT + `auto=true` + fingerprint」，**不再要求** `pairing_code`；access_key 路径保留。配对码流程保留给无登录场景/共享临时加入。
- **方案 B：** 新增 `POST /devices/auto-enroll`，语义同 A，旧 enroll 不动。

无论 A/B：成功响应仍为 `{ device, device_token }`，设备通道仍只用 `odv_`，**禁止**把账号密码或长期 access_key 存进设备 WS 状态。

### 5.2 断线 / 重启后恢复上线

1. 执行端用本地 state 的 `device_id` + `odv_` 直接 `hello`；
2. 成功 → 心跳保活，指挥端变绿；
3. 票失效（撤销/轮换）→ 提示重新账号登录走 5.1 合并；
4. **禁止**在无用户确认时静默用账号密码重登获取新票（可提示；无人值守场景仅允许事先配置的 access_key/key-file，且仍发 `odv_`）。

### 5.3 指挥端「看见设备网」

- `GET /devices`：当前登录账号的全部未撤销设备 + online / last_seen；
- 多指挥端共享同一中枢列表（无第二套同步）；
- 手机浏览器同权（指挥）；不因 UA 过滤设备。

### 5.4 撤销与踢出

- 指挥端 `POST /devices/{id}/revoke`：断开 WS、拒绝新操作、本地票作废；
- 撤销后同 fingerprint 再次 auto-enroll：**默认需指挥端确认**（防「撤了又自动回来」）；设置项可改为「允许自动重新登记」（高级）；
- 账号密码修改 / 全局吊销 access_key：**不自动**删除设备登记，但可使依赖该 key 的待登记失败；已发 `odv_` 是否连坐吊销 → 建议 **可选「吊销该账号全部设备票」** 按钮，默认不连坐（与 0001 AC-10 精神一致：设备票与账号 key 分离）。

### 5.5 权限变更

- 自动登记后的默认 grant 可在设备页升级/降级（沿用 PATCH permissions / roots）；
- `grant_version` bump；在途操作按 contract 拒绝过期 grant；
- 命令执行、键鼠、ACP 等敏感能力：**不**进默认自动授权（§6）。

## 6. 权限与安全

### 6.1 自动登记默认权限（MVP 建议）

| 能力 | 默认 | 说明 |
|---|---|---|
| `files_read` | 开（若用户选了共享根） | 无共享根则仅 ping/status |
| `files_write` | 关 | 需显式开 |
| `desktop_view` | 关 | Win 可稍后开 |
| `desktop_control` | 关 | 始终显式 |
| `command_exec` | 关 | 始终显式 + HITL 策略保留 |
| `acp_run` | 关 | 需设备 `--allow-acp` + 登记授权 |

首启 UI 可勾选「常用办公包」（例如：只读桌面目录 + 桌面查看），但不得默认全开。

### 6.2 安全不变式（必须）

1. **双凭据：** 指挥 = 用户会话；执行 = `odv_`。账号登录只用于签发/恢复设备票，不替代设备通道认证。  
2. **票不进 URL / 日志；** 推荐 key-file / 系统凭据库存 state。  
3. **中枢可达性：** 执行端必须能连中枢（LAN/VPN/HTTPS）；不做局域网盲扫「发现未登录设备」。  
4. **HTTPS：** 生产与跨机传文件/ACP 应按既有要求升级；HTTP 仅 loopback 或显式 insecure。  
5. **同账号 ≠ 同信任边界外泄：** 能打开登录页的网络暴露面仍靠防火墙/绑定地址收紧（与启动器 host 选择一致）。  
6. **撤销优先于方便：** 撤销后的自动复活必须可关，默认需确认。

### 6.3 威胁与缓解（摘录）

| 威胁 | 缓解 |
|---|---|
| 偷到账号密码冒登记新设备 | 登录二次验证（可选后续）；新设备通知；默认最小权限 |
| 偷到 `odv_` | 权限同该设备；撤销即废；文件权限收紧 |
| 配对码被蹭用 | 自动登记主路径不再依赖配对码；配对码保留短时+单次 |
| 中枢被伪冒 | HTTPS + 证书固定/私有 CA（后续）；禁止明文提交密码到陌生 host（UI 警告） |

## 7. 与 device_binding / ACP 的关系

- **不冲突：** 自动登记只解决「设备如何进入账号的网」；专家 `device_binding` 仍绑定已登记的 `device_id` + 可读写根。  
- **顺序：** 先自动登记且设备在线 → 再在专家编辑页绑定 → 设备需具备 `acp_run` 授权与 `--allow-acp`。  
- **失败语义保持：** 设备离线 / 无 `acp_run` / 根失效 / runner 未装 → 调用失败，**不**回落到中枢本机偷偷执行（device-acp 已述）。  
- **手机：** 可指挥绑定了 Win/Linux 设备的专家；手机自己成为 ACP 执行机 = 后续「手机可执行」阶段，不在本 MVP。

## 8. MVP 分期

### MVP-1（本规格主交付）— 「登账号进网」

1. 执行端账号登录（密码或 devices 向 access_key）→ auto-enroll / fingerprint 合并；  
2. 指挥端列表实时在线；断线恢复不重复设备；  
3. 默认最小权限 + 设备页改授权；  
4. 保留旧配对码 enroll，兼容已有脚本；  
5. 文档与首启文案改为 UU 心智（「登录同一账号」）。

**验收焦点：** 工位中枢 + 笔记本执行端 +（可选）工位本机执行端；无需手抄配对码完成进网与派活 ping/files.list。

### MVP-2 — 「体验硬化」

1. 新设备登录通知（站内/通道）；撤销后默认需确认才可再自动登记；  
2. HTTPS 前提下的跨机文件往返验收；  
3. GPU（Linux）走同一自动登记路径；  
4. 开机自启执行端 + 真重启后自动上线验收。

### MVP-3 — 「手机可执行」（仅立项，不设计细节）

1. 手机执行端 App/自动化运行时；  
2. 能力模型（通知、无障碍、指定 App 自动化等）另开规格；  
3. 本阶段手机继续仅 Commander。

### 明确延后

- 中枢扫网/UDP 发现未登录机器；  
- 多中枢热备与跨库设备合并；  
- 无账号的「局域网随便进」；  
- 用浏览器登录态直接当设备 WS 认证。

---

## 9. 非目标

1. 改变「单中枢」拓扑或引入 UU 式 P2P 无中枢；  
2. 登录网页就自动变成执行设备；  
3. 多账号设备网互通 / 团队共享设备池（可另规）；  
4. 替换现有 operation ledger、文件分块中继、grant_version 机制；  
5. 本阶段交付手机执行端或移动 ACP；  
6. 公有云中继服务（中枢自迁云 ≠ 托管中继）。

## 12. 待用户拍板（评审问题）

1. 自动登记默认权限包：是否接受 §6.1「最小权限」还是希望「办公只读包」预置？  
2. 撤销后再次自动登记：默认「需确认」还是「允许自动复活」？  
3. API 形态：扩展现有 `/devices/enroll`（方案 A）还是新 `/devices/auto-enroll`（方案 B）？  
4. 账号密码登录执行端是否允许（本机 UI），还是 MVP 只推 access_key/key-file 以降低密码落盘面？  
5. fingerprint 合并是否在 MVP-1 必须具备，还是先「有 state 则恢复、无 state 则新建」足够？

## 13. 建议实现落点（仅指引，本 DRAFT 不改代码）

- 服务端：`infra/devices/service.py`、`api/routers/devices`、DB devices 表增加 fingerprint 唯一性（按 owner 范围）；  
- 客户端：`cli/device_cmd.py` / 首启向导 / portable `start-device`：账号登录 → auto-enroll；  
- UI：Devices 页文案与「新设备」标记；  
- 文档：更新 contract 与 verification 对应用例；  
- **不**修改 Agent 派工与 ACP 绑定逻辑，仅消费已登记设备。
